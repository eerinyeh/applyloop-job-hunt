# Existing tracker import

This is an agent-assisted spreadsheet migration, not a generic one-command importer. `tracker.py read_xlsx` reads this project's own Applications schema only. Do not feed it an arbitrary uploaded workbook and claim general import support. Use the available spreadsheet skill to inspect XLSX/CSV sources and author/verify the migration.

1. Preserve the source under private with a source manifest. Inspect actual sheets, header rows, date system, formulas and rows; keep all original fields. Ask only consequential questions such as which sheet contains applications or whether an ambiguous date is day-first. A formula cache alone is not reliable status evidence.
2. Map employer, role, advert, requisition, submission date, status, category and notes to the new contract. Retain old IDs, unmatched columns, raw status wording and source sheet/row in a private migration ledger. Use explicit dates only; missing submission dates remain unresolved and are not counted in dated metrics. Do not infer submission from creation/updated dates or invent first progression dates from current Interview/Rejected status.
3. Review category aliases against the confirmed new directions. Historical categories can remain separate confirmed reporting categories, without requiring a base CV for each. An explicitly accepted Uncategorised reporting category can retain uncertain history. Do not silently force old applications into a new search direction.
4. Check duplicates against both uploaded rows and current applications using actual requisitions and advert identities. Company/title is only a possible duplicate; separate roles or repeat applications may share those values. Never merge contradictory statuses or dates by choosing an arbitrary 'latest' value. Present conflicts and proposed merges for resolution.
5. Save a reconciliation preview: original row count, distinct application candidates, proposed imports/merges and unresolved records. Keep every source row accounted for in the migration ledger, including duplicates and pending review. Show consequential status/date/category mappings for confirmation before adopting them.
6. Build a new workbook from confirmed categories if there is no target; merge carefully into an existing populated target with a backup otherwise. Unknown historical priorities stay unknown; historically recorded priority 1–2 rows are preserved, not excluded by today's triage gate. Do not invent historical preference scores. The current template/update helper assumes priority 3–5 and known progression dates for progressed states, so incompatible historical rows require a reviewed schema/metrics adaptation using the spreadsheet skill, or remain in a clearly reported private pending-import file. Do not quietly coerce them to fit the updater.
7. Recalculate, render and check imported dates/statuses, filters/search, duplicate IDs and cohort totals. Reconcile source/import/merge/pending counts. Deliver a concise summary of remaining unresolved rows. Keep the source unchanged and support correction from the ledger.

Importing old applications does not create full JD packets or reconstructed CVs when those sources are absent. Mark missing advert text as unavailable. A later employer message can still match by confirmed requisition/thread/company and role. This migration branch has instructions but needs a real supplied tracker and verified run before claiming support for its format.
